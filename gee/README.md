# Environmental feature export in Google Earth Engine

`extract_features.js` contains the author-supplied `corrected_v1` calculations. Release-only edits replace the private asset reference with a configurable value, remove a duplicate declaration, and normalize the identifier to `Well_ID`. The scientific calculations and original date range are retained.

## Run the export

1. Open the authenticated [Earth Engine Code Editor](https://code.earthengine.google.com/).
2. In **Assets > New > CSV**, upload `wells.csv`. Use `longitude` as X and `latitude` as Y in WGS84/EPSG:4326, and retain `Well_ID` as a string. The table contains the 22 candidate locations from the supplied metadata; the Python groundwater panel selects its 20 model nodes.
3. Wait for ingestion to complete. Copy the resulting asset ID into `WELL_ASSET_ID` at the top of `extract_features.js`.
4. Paste the script into a new JavaScript editor tab and run it. Check the preview and well identifiers.
5. In **Tasks**, start the `Haouz_features_corrected_v1` table export. It writes CSV to the `earthengine` folder in Google Drive. Earth Engine access and Drive export authorization must be supplied by the person running it.
6. Download the CSV to a **new** filename, inspect its dates, keys, units, masks and coverage, then run the merge CLI against it explicitly. Preserve the archived training export and its hashes.

Google's [table upload documentation](https://developers.google.com/earth-engine/guides/table_upload) describes the CSV coordinate fields and ingestion steps.

## Aggregation and quality controls

The period is January 2006--December 2022 (end date `2023-01-01` is exclusive). Sampling uses `reduceRegions`, mean reducer, scale 500 m and `tileScale: 4` over each uploaded feature's geometry. Here the uploaded features are well points; no buffer is added. The 500 m analysis scale does not imply 500 m native resolution for every source. No explicit CRS or resampling kernel is selected.

MODIS 8/16-day composites are clipped at calendar-year boundaries and weighted by overlap days with each month. ET totals are divided by composite length before allocating overlap; LST/NDVI use valid-day weighted means. Coverage columns are valid overlap-day fractions. ET scales by 0.1 and requires QC bit 0 = 0, SCF QC <= 1, and raw ET in [0,32700]. LST requires the two mandatory QC bits to equal 0 and converts using 0.02 K minus 273.15. NDVI scales by 0.0001 and requires `SummaryQA == 0`.

Landsat uses the lower six QA_PIXEL bits clear, QA_RADSAT = 0, reflectance scale 0.0000275 with offset -0.2, and a positive red+NIR denominator. Available scenes are averaged within each month, with a scene count. CHIRPS is summed; ERA5 runoff/snow terms are converted from metres to millimetres and evaporation changes sign. TerraClimate PDSI and deficit use 0.01 and 0.1, respectively; GLDAS soil fields are monthly means. WaPOR's supplied rate is integrated by overlap days after its scale factor. The model uses MODIS ET, not a groundwater-ET partition or WaPOR pumping estimate.

## Reproducibility limits

The archived `data/Haouz_features_corrected_v1.csv` ends in November 2022 and lacks the two WaPOR output columns present in this script. Retain those differences in provenance; a fresh export must be independently checked. GEE execution, asset access and numerical equality with the archived CSV have not been validated during packaging. Satellite product updates and availability can affect re-exports.

[MOD16A2GF is a year-end gap-filled product](https://developers.google.com/earth-engine/datasets/catalog/MODIS_061_MOD16A2GF). These experiments use retrospective archived features. Chronological input windows alone do not demonstrate that the upstream products/composites were available at the forecast issue date; an operational deployment needs release-delay and compositing checks. [WaPOR catalog documentation](https://developers.google.com/earth-engine/datasets/catalog/FAO_WAPOR_2_L1_AETI_D) provides the separate product description and terms.
